# Decision log

Format: `D-<n> (date) — decision. Why. Consequence.` Newest at bottom. Contracts in REPLAY_PLAN.md §4.5/§4.6 are the source of truth; deviations are recorded here.

## D-1 (2026-09-22) — Phase 1 targets a browser-based TV client, not react-native-tvos
Phase 1 runs entirely local with no Fire TV hardware. The TV UI (`apps/web`, route `/tv`) is a React + Vite web app driven by keyboard D-pad emulation (Arrow keys = D-pad, Enter = Select, Escape/Backspace = Back, Space = Play/Pause, `,`/`.` = −/+10 s, `[`/`]` = previous/next event, `b` = bookmark). All platform-specific code stays behind `PlayerSurface` and `platform/` per plan §4.8 so the RN/Vega port reuses screens, overlays and spatial focus. Consequence: Playwright can drive the entire product end-to-end; the RN port is Phase 3 work.

## D-2 (2026-09-22) — One Vite app serves uploader (`/upload`) and TV (`/tv`)
Fewer packages, one dev server, one Playwright config. Split later if the RN port needs it.

## D-3 (2026-09-22) — Phase 1 media is progressive MP4 with HTTP range requests, not HLS
Chromium does not play HLS natively and Phase 1 has no TV device. Ingest writes a faststart H.264 30 fps mezzanine (`media/wide.mp4`) and the API serves it with range support. `renditions.wide` in game.json points at that MP4. HLS ladder is added when the Fire OS/Vega client exists (Phase 3). Schema unchanged: `renditions.wide` is just a URL.

## D-4 (2026-09-22) — `courtcam` lives in this repo under `courtcam/` for now
Developed as its own package (own pyproject, MIT LICENSE, README, tests) so `git subtree split -P courtcam` can create the public repo with history intact. `services/api` depends on it via a uv workspace, not vendoring.

## D-5 (2026-09-22) — Python 3.12 via uv workspace; YOLO11n + ultralytics built-in ByteTrack on CPU
Python 3.14 (system) is not supported by ultralytics/torch wheels yet. No NVIDIA GPU on the dev box; detection runs on CPU at stride 2 (15 Hz) with `yolo11n.pt` at imgsz 960 (bump to 1280 if small players are missed). Tracking uses `model.track(tracker="bytetrack.yaml", persist=True)` rather than a separate ByteTrack dependency.

## D-6 (2026-09-22) — Follow-cam default is `client` mode on web
`<video>` inside a fixed-size viewport, CSS `transform: translate(...) scale(...)` from the crop rect each animation frame. `rendition` mode (ffmpeg pre-render) is the fallback, implemented lazily after the core loop works.

## D-7 (2026-09-22) — Test corpus policy
Real footage under `samples/real/` is gitignored and used for local testing only. Each downloaded clip is recorded in `samples/real/MANIFEST.md` with source URL, license/terms as observed, and why it matches the target framing (fixed tripod, whole court, phone-quality). Synthetic clips under `samples/synthetic/` are generated by a script and are the CI fixture.

## D-8 (2026-09-22) — Git conventions
Commit message: `<feat|fix|chore>: one-line message`. Subagents never run git; the orchestrator commits per stage.

## D-9 (2026-09-22) — `game.json` is owned by courtcam during a run
courtcam rewrites `game.json` after every stage. The API writes it only at job creation (schema-valid stub) and completion; per-stage progress lives in the job record (`data/jobs.json`) and is merged into `GET /games/{id}` responses. Fake pipeline mode copies the fixture tree except `game.json`. Library index is a glob over `data/games/*/game.json` — no SQLite in Phase 1 (one process, tens of games).

## D-10 (2026-09-22) — H.264 encoder selection
Dev box ffmpeg has no `libx264`; encoders are tried in order `libx264` → `h264_vaapi`/`h264_qsv` (if available) → `libopenh264` → stream copy. Any tool that encodes must go through this fallback, never hardcode `libx264`.

## D-11 (2026-09-22) — "Not a shot" is an additive `dismissed` flag on the event, not a retype
The review queue's third answer used to rewrite `type` to `possession_change`, which lies about
what happened and pollutes a real event type. Instead `PATCH /games/{id}/events/{eid}` accepts
`{"dismissed": true, "confirmed": true}` and the API sets `source: "user"` as it does for any
correction. `replay.events.v1` is unchanged and `dismissed` is optional; courtcam's pydantic
models are `extra="allow"`, so a file the API rewrote still round-trips through courtcam.
Consequence: `POST /games/{id}/query` and `GET /games/{id}/stats` filter dismissed events out;
they stay in `events.json` so the decision is reversible.

## D-12 (2026-09-22) — `GET /games/{id}/stats` is `{box_score, shots, heatmap, totals}`
§4.6 only says "derived box score lite, shot chart points, heatmap grid". The API now returns
exactly what the TV's Review screen renders: `box_score: [{player_id, name, team, attempts,
makes, confirmed, confidence, distance_m, samples}]`, `shots: [{event_id, player_id, court,
made, confirmed, confidence}]`, `heatmap: [{player_id, cols, rows, x_range, y_range, values}]`
(`values` row-major, `cols * rows` long) and `totals: {attempts, makes}`. Consequence: R4
distance covered rides along in `box_score` even though no screen shows it yet.

## D-13 (2026-09-22) — Response shapes the plan left open: bare arrays, `thumb_url`, `id`
Reconciling `apps/web` against `services/api`, all unspecified by §4.6:
`GET /sports` and `GET /games` return bare JSON arrays (no `{"sports": …}` / `{"games": …}`
envelope), matching `/query` and `/stats` which already did. A sport profile repeats its
`court.landmarks` / `court.variants` at the top level as `landmarks` / `variants` — the click
order is a client concern, the nested block stays for the pipeline — and `sport_ui.court` is
normalised to `{size_m, x_range, y_range, polygons}` in metres so the TV can draw a court whose
origin is the baseline centre. `GET /games` uses `thumb_url`, not `thumbnail`, matching
`events_url` / `calib_url`. `POST /sessions` returns `{id, code}` like every other create.
`POST /games/{id}/calibration` takes `{sport, variant, landmarks_px}` — the web client maps its
internal `court_variant` on the way out and flattens the 200/400 into `{ok, …}`.

## D-14 (2026-09-22) — The calibration frame is grabbed at upload, not by the pipeline
Calibration happens before processing, so `media/wide.mp4` and `media/thumb.jpg` do not exist
yet when `/upload/:id/calibrate` needs an image. The upload handler runs one
`ffmpeg -ss 5 -frames:v 1` (falling back to the first frame for short clips) into
`media/calib.jpg`, and `GET /games/{id}` exposes it as `calib_url` next to `thumb_url` and
`sport_ui`. Cost is ~100 ms on a local file. Consequence: landmark pixel coordinates are in the
source video's frame space, which is also what the pipeline homography expects.

## D-15 (2026-09-22) — courtcam schema notes
`Event.made` is `bool | null` (`null` = not judged by the heuristic labeler, distinct from `false`). A profile may declare `court.templates: {variant: file}` instead of `court.template` (basketball needs one template per variant). Field names are unchanged from §4.5. courtcam owns `game.json` during a run (D-9); `out/_work/` holds intermediates the API never serves.

## D-16 (2026-09-22) — `WS /sessions/{sid}` also accepts the 4-digit pairing code
The phone companion (`/companion`, H4) only ever sees the code the TV shows, so it would
need a `GET /sessions/by-code/{code}` round trip before it could open the socket. Instead
the WebSocket route resolves `{sid}` as either a session id (`s_…`) or a pairing code
(four digits) — the two can never collide. No new route, no lookup, and an unknown value
still closes the socket with 4404, which the phone renders as "that code is not paired".
Consequence: `POST /sessions` stays the only session route; `AC-13` covers both forms.

## D-17 (2026-09-22) — live stage progress is merged into the read path, plus `progress`
D-9 said per-stage progress lives in the job record; this is how it reaches clients.
`GET /games/{id}` and `GET /games` merge the newest queued/running `process` job from
`data/jobs.json`: `status` becomes `processing`, the job's current stage is `running`
(`done` once its fraction hits 1.0), earlier stages are `done`, later ones `pending`, and
an additive `progress: {stage: fraction}` object rides along (absent when no job is
running). `game.json` is never written mid-run. `POST /games/{id}/process` is idempotent:
while a job for that game is queued or running it returns 202 with that job's id instead
of queuing a second run. `REPLAY_FAKE_PIPELINE_DELAY_S` (default 0) sleeps between the
two progress reports of each fake stage so the transition is observable in tests.

## D-18 (2026-09-22) — Lens distortion is out of Phase 1 scope
Every clip in the test corpus is ultra-wide or panoramic-stitched, so a single homography cannot sit on the court lines (see samples/real/RESULTS.md). The target footage is a phone 1x lens on a tripod, which is far less distorted. Phase 1 keeps the plain homography (least-squares over all clicked landmarks, optional extras allowed) and accepts loose on-court filtering on the corpus. Upgrade path: estimate k1/k2 from straight court lines with `cv2.calibrateCamera` before the homography. The uploader should tell users to film with the 1x lens, not 0.5x.

## D-19 (2026-09-22) — calibration takes any 4 landmarks the template knows, and the gate scales with the clicked span
Driving the real uploader on `basketball_kennesawwide_smoke.mp4` (2560×960 panoramic,
`corner_fr` off the bottom of the frame) failed three ways, all of them contract, not code:
`POST /games/{id}/calibration` demanded 4 `corner_*` **and** every name in
`court.landmarks`; the phone column showed the frame at 560 CSS px, so one tap was worth
~4.6 source px; and `MAX_REPROJ_PX = 5.0` is an absolute pixel bar. The fit on this
footage is barrel distorted (D-18) and ill-conditioned — ±0.5 px of click noise already
costs ~3.5 px of reprojection error, and guessing `corner_fr` on-frame costs ~20 px
(2000 px once the optional landmarks are in), far worse than leaving it out.
So: the API requires **4 landmarks the template knows** (`landmarks` ∪
`landmarks_optional`) and nothing more; the uploader walks the required list, lets any
single point be skipped ("Not visible") and reveals `landmarks_optional` behind a "More
points" button; the calibrate screen escapes the 560 px column; and the gate is
`max(5 px, 1 % of the clicked landmarks' pixel span)` — 25 px on this clip, still 5 px on
a 720p one. Measured: the polygon from hand clicks at 1920 px sits within ~25 px of the
one from exact landmarks, which is well inside `margin_m`. The web client no longer
carries its own copy of the threshold; a 200 from the API means "usable".
Consequence: `POST /games/{id}/calibration` no longer 400s on a missing `rim`.

## D-20 (2026-09-22) — the follow-cam window is a fraction of the COURT, and it is 16:9
`followcam.zoom` divided the *frame* width, so the same 2.0 meant a tight crop on a 720p
clip and half of a 2560 px whole-court panorama. It now divides the court's pixel width
(`calib.court_polygon_px`, clipped to the frame; `croppath.court_px_width`), with
`croppath.MIN_CROP_W` as the floor and the frame width as both the cap and the fallback
when there is no calibration. The window is 16:9 in source pixels rather than the
frame's aspect, because the TV viewport is 16:9 — so `PlayerSurface` scales x and y
independently (identical to the old uniform scale on a 16:9 source) and
`render.render_crop` sizes its output from the crop rect instead of the source. Without
that pair a 2560×960 source came out stretched 1.5× vertically in follow mode.

## D-21 (2026-09-22) — `players.max` is a concurrency cap, not a roster size
The global top-N cap left 2–3 selectable players late in a clip because the best-scoring merged players were not contemporaneous. `identity` now accepts players greedily by score as long as no instant exceeds `players.max` concurrent players; the roster in `game.json` may exceed `max` (57 on the 240 s Kennesaw clip). Player ids are assigned in acceptance order. See samples/real/RESULTS.md "Concurrency cap".

## D-22 (2026-09-22) — No lens-distortion model; the badminton corpus clip fails on resolution, not barrel
Measured on the two net-sport clips: the 1x pickleball clip fits a 10-landmark homography at 2.8 px reprojection with ≤ 2.2 px paint drift, so nothing to correct. The 0.5x badminton clip compresses the 13.41 m court into 168 px of image height (≈ 3.4 px/m at the far baseline) with three overlapping line systems and two courts; undistortion cannot create the missing pixels. Decision: no `distortion.py`; `landmarks_optional` plus the reprojection gate handle usable wide-lens clips. Revisit only if a clip fails the gate with residuals that grow with radius from the image centre. Corollary for users and the corpus: a net-sport camera must be above and behind a baseline (≈ 3 m up), framing one court. Badminton stays "Tier 1 by code path" until a usable clip exists.

## D-23 (2026-09-22) — Auto-calibration proposes landmarks; the user still commits them
`courtcam.autocalib` proposes landmark pixels (backends: `vlm` via Anthropic SDK, `claude-cli` for keyless local dev, `lines` OpenCV snapping; `auto` chains them with a two-pass mirror-agreement gate and the D-19 reprojection gate). The API exposes it as a job (`POST/GET /games/{id}/calibration/auto`) and the phone page shows the proposal for accept or drag-adjust; `POST /calibration` remains the only commit. Status: on the panoramic corpus the model traces the wrong line (0 of 3 basketball clips within 20 px), so the UI currently hands users dots to drag rather than dots to accept. Next attempt: fit the court template to detected lines (classic) with the model as a prior; evaluate on phone footage when it exists.

## D-24 (2026-09-22) — Auto-calibration default is a template fit, not a vision model
`autocalib`'s `auto` backend is `templatefit`: line mask → Hough → merged lines → convex quads from line pairs matched to template rectangles whose edges are painted → scored by projecting the whole template against a distance transform → corner refinement. Measured: 10/10 landmarks within 12 px on the 1x pickleball clip and 1.8 px on the synthetic fixture, in 4–12 s with no key or network; the vision-model backends scored 0 of 4 at ~$0.26 and 3–14 min per clip and remain opt-in (`vlm`, `claude-cli`) or usable as a `--prior`. It fails on the three panoramic basketball clips because a barrel-distorted edge is a curve, and the hand-made homographies there score 0.23–0.27 against the paint themselves. `ok` is gated on the line score (≥ 0.90), not on reprojection error, which is 0 by construction for this backend. Next: run the fit on an undistorted frame once the distortion model (D-25 pending) exists.

## D-25 (2026-09-22) — One-parameter lens model, gated (supersedes D-22's "no distortion model")
The badminton auditorium clip (GoPro superview, camera beside the court in the net plane) met D-22's revisit criterion: pinhole residuals grow with radius (3 px at the centre, 25 px at 400–600 px). `courtcam.distortion` fits a division-model `k1` about the image centre at the calibrate stage from the clicked landmarks alone, gated at ≥ 8 landmarks and ≥ 30 % rms reduction, else `k1 = 0` (bit-identical to the previous payload; synthetic golden unchanged). `calib.json` gains additive `k1`, `image_size`, `lens_rms_px`; the court polygon becomes a 0.25 m polyline that curves with the paint; foot points are undistorted before projection. Result on that clip: rms 14.6 → 2.5 px, metre error 0.47 → 0.09 m max, roster unchanged (empty hall), team-by-side 0 errors in 14 026 samples. Ceiling: one parameter about the frame centre; `basketball_ceilingcam` (landmarks within 0.54 of the half-diagonal, 8 px/m depth, near corners occluded) leaves the gate closed and is not calibratable. Known follow-ups: `calibrate.homography()` RANSAC can report a 5-point consensus error on a barrelled frame; the API's calibration preview must call the lens-aware fit.
