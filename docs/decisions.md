# Decision log

Format: `D-<n> (date) — decision. Why. Consequence.` Newest at bottom. Contracts in REPLAY_PLAN.md §4.5/§4.6 are the source of truth; deviations are recorded here.

## D-1 (2026-09-22) — Phase 1 targets a browser-based TV client, not react-native-tvos
Phase 1 runs entirely local with no Fire TV hardware. The TV UI (`apps/web`, route `/tv`) is a React + Vite web app driven by keyboard D-pad emulation (Arrow keys = D-pad, Enter = Select, Escape/Backspace = Back, Space = Play/Pause, `,`/`.` = −/+10 s, `[`/`]` = previous/next event, `b` = bookmark). All platform-specific code stays behind `PlayerSurface` and `platform/` per plan §4.8 so the RN/Vega port reuses screens, overlays and spatial focus. Consequence: Playwright can drive the entire product end-to-end; the RN port is Phase 3 work.

## D-2 (2026-09-22) — One Vite app serves uploader (`/upload`) and TV (`/tv`)
Fewer packages, one dev server, one Playwright config. Split later if the RN port needs it.

## D-3 (2026-09-22) — Phase 1 media is progressive MP4 with HTTP range requests, not HLS
Chromium does not play HLS natively and Phase 1 has no TV device. Ingest writes a faststart H.264 30 fps mezzanine (`media/wide.mp4`) and the API serves it with range support. `renditions.wide` in game.json points at that MP4. HLS ladder is added when the Fire OS/Vega client exists (Phase 3). Schema unchanged: `renditions.wide` is just a URL.

## D-4 (2026-09-22) — `courtcam` lives in this repo under `courtcam/` for now
Developed as its own package (own pyproject, MIT LICENSE, README, tests) so `git subtree split -P courtcam` can create the public repo with history intact. `services/api` depends on it via a uv workspace, not vendoring.

## D-5 (2026-09-22) — Python 3.12 via uv workspace; YOLO11n + ultralytics built-in ByteTrack on CPU
Python 3.14 (system) is not supported by ultralytics/torch wheels yet. No NVIDIA GPU on the dev box; detection runs on CPU at stride 2 (15 Hz) with `yolo11n.pt` at imgsz 960 (bump to 1280 if small players are missed). Tracking uses `model.track(tracker="bytetrack.yaml", persist=True)` rather than a separate ByteTrack dependency.

## D-6 (2026-09-22) — Follow-cam default is `client` mode on web
`<video>` inside a fixed-size viewport, CSS `transform: translate(...) scale(...)` from the crop rect each animation frame. `rendition` mode (ffmpeg pre-render) is the fallback, implemented lazily after the core loop works.

## D-7 (2026-09-22) — Test corpus policy
Real footage under `samples/real/` is gitignored and used for local testing only. Each downloaded clip is recorded in `samples/real/MANIFEST.md` with source URL, license/terms as observed, and why it matches the target framing (fixed tripod, whole court, phone-quality). Synthetic clips under `samples/synthetic/` are generated by a script and are the CI fixture.

## D-8 (2026-09-22) — Git conventions
Commit message: `<feat|fix|chore>: one-line message`. Subagents never run git; the orchestrator commits per stage.

## D-9 (2026-09-22) — `game.json` is owned by courtcam during a run
courtcam rewrites `game.json` after every stage. The API writes it only at job creation (schema-valid stub) and completion; per-stage progress lives in the job record (`data/jobs.json`) and is merged into `GET /games/{id}` responses. Fake pipeline mode copies the fixture tree except `game.json`. Library index is a glob over `data/games/*/game.json` — no SQLite in Phase 1 (one process, tens of games).

## D-10 (2026-09-22) — H.264 encoder selection
Dev box ffmpeg has no `libx264`; encoders are tried in order `libx264` → `h264_vaapi`/`h264_qsv` (if available) → `libopenh264` → stream copy. Any tool that encodes must go through this fallback, never hardcode `libx264`.
