# Decision log

Format: `D-<n> (date) — decision. Why. Consequence.` Newest at bottom. Contracts in REPLAY_PLAN.md §4.5/§4.6 are the source of truth; deviations are recorded here.

## D-1 (2026-09-22) — Phase 1 targets a browser-based TV client, not react-native-tvos

Phase 1 runs entirely local with no Fire TV hardware. The TV UI (`apps/web`, route `/tv`) is a React + Vite web app driven by keyboard D-pad emulation (Arrow keys = D-pad, Enter = Select, Escape/Backspace = Back, Space = Play/Pause, `,`/`.` = −/+10 s, `[`/`]` = previous/next event, `b` = bookmark). All platform-specific code stays behind `PlayerSurface` and `platform/` per plan §4.8 so the RN/Vega port reuses screens, overlays and spatial focus. Consequence: Playwright can drive the entire product end-to-end; the RN port is Phase 3 work.

## D-2 (2026-09-22) — One Vite app serves uploader (`/upload`) and TV (`/tv`)

Fewer packages, one dev server, one Playwright config. Split later if the RN port needs it.

## D-3 (2026-09-22) — Phase 1 media is progressive MP4 with HTTP range requests, not HLS

Chromium does not play HLS natively and Phase 1 has no TV device. Ingest writes a faststart H.264 30 fps mezzanine (`media/wide.mp4`) and the API serves it with range support. `renditions.wide` in game.json points at that MP4. HLS ladder is added when the Fire OS/Vega client exists (Phase 3). Schema unchanged: `renditions.wide` is just a URL.

## D-4 (2026-09-22) — `courtcam` lives in this repo under `courtcam/` for now

Developed as its own package (own pyproject, MIT LICENSE, README, tests) so `git subtree split -P courtcam` can create the public repo with history intact. `services/api` depends on it via a uv workspace, not vendoring.

## D-5 (2026-09-22) — Python 3.12 via uv workspace; YOLO11n + ultralytics built-in ByteTrack on CPU

Python 3.14 (system) is not supported by ultralytics/torch wheels yet. No NVIDIA GPU on the dev box; detection runs on CPU at stride 2 (15 Hz) with `yolo11n.pt` at imgsz 960 (bump to 1280 if small players are missed). Tracking uses `model.track(tracker="bytetrack.yaml", persist=True)` rather than a separate ByteTrack dependency.

## D-6 (2026-09-22) — Follow-cam default is `client` mode on web

`<video>` inside a fixed-size viewport, CSS `transform: translate(...) scale(...)` from the crop rect each animation frame. `rendition` mode (ffmpeg pre-render) is the fallback, implemented lazily after the core loop works.

## D-7 (2026-09-22) — Test corpus policy

Real footage under `samples/real/` is gitignored and used for local testing only. Each downloaded clip is recorded in `samples/real/MANIFEST.md` with source URL, license/terms as observed, and why it matches the target framing (fixed tripod, whole court, phone-quality). Synthetic clips under `samples/synthetic/` are generated by a script and are the CI fixture.

## D-8 (2026-09-22) — Git conventions

Commit message: `<feat|fix|chore>: one-line message`. Subagents never run git; the orchestrator commits per stage.

## D-9 (2026-09-22) — `game.json` is owned by courtcam during a run

courtcam rewrites `game.json` after every stage. The API writes it only at job creation (schema-valid stub) and completion; per-stage progress lives in the job record (`data/jobs.json`) and is merged into `GET /games/{id}` responses. Fake pipeline mode copies the fixture tree except `game.json`. Library index is a glob over `data/games/*/game.json` — no SQLite in Phase 1 (one process, tens of games).

## D-10 (2026-09-22) — H.264 encoder selection

Dev box ffmpeg has no `libx264`; encoders are tried in order `libx264` → `h264_vaapi`/`h264_qsv` (if available) → `libopenh264` → stream copy. Any tool that encodes must go through this fallback, never hardcode `libx264`.

## D-11 (2026-09-22) — "Not a shot" is an additive `dismissed` flag on the event, not a retype

The review queue's third answer used to rewrite `type` to `possession_change`, which lies about
what happened and pollutes a real event type. Instead `PATCH /games/{id}/events/{eid}` accepts
`{"dismissed": true, "confirmed": true}` and the API sets `source: "user"` as it does for any
correction. `replay.events.v1` is unchanged and `dismissed` is optional; courtcam's pydantic
models are `extra="allow"`, so a file the API rewrote still round-trips through courtcam.
Consequence: `POST /games/{id}/query` and `GET /games/{id}/stats` filter dismissed events out;
they stay in `events.json` so the decision is reversible.

## D-12 (2026-09-22) — `GET /games/{id}/stats` is `{box_score, shots, heatmap, totals}`

§4.6 only says "derived box score lite, shot chart points, heatmap grid". The API now returns
exactly what the TV's Review screen renders: `box_score: [{player_id, name, team, attempts,
makes, confirmed, confidence, distance_m, samples}]`, `shots: [{event_id, player_id, court,
made, confirmed, confidence}]`, `heatmap: [{player_id, cols, rows, x_range, y_range, values}]`
(`values` row-major, `cols * rows` long) and `totals: {attempts, makes}`. Consequence: R4
distance covered rides along in `box_score` even though no screen shows it yet.

## D-13 (2026-09-22) — Response shapes the plan left open: bare arrays, `thumb_url`, `id`

Reconciling `apps/web` against `services/api`, all unspecified by §4.6:
`GET /sports` and `GET /games` return bare JSON arrays (no `{"sports": …}` / `{"games": …}`
envelope), matching `/query` and `/stats` which already did. A sport profile repeats its
`court.landmarks` / `court.variants` at the top level as `landmarks` / `variants` — the click
order is a client concern, the nested block stays for the pipeline — and `sport_ui.court` is
normalised to `{size_m, x_range, y_range, polygons}` in metres so the TV can draw a court whose
origin is the baseline centre. `GET /games` uses `thumb_url`, not `thumbnail`, matching
`events_url` / `calib_url`. `POST /sessions` returns `{id, code}` like every other create.
`POST /games/{id}/calibration` takes `{sport, variant, landmarks_px}` — the web client maps its
internal `court_variant` on the way out and flattens the 200/400 into `{ok, …}`.

## D-14 (2026-09-22) — The calibration frame is grabbed at upload, not by the pipeline

Calibration happens before processing, so `media/wide.mp4` and `media/thumb.jpg` do not exist
yet when `/upload/:id/calibrate` needs an image. The upload handler runs one
`ffmpeg -ss 5 -frames:v 1` (falling back to the first frame for short clips) into
`media/calib.jpg`, and `GET /games/{id}` exposes it as `calib_url` next to `thumb_url` and
`sport_ui`. Cost is ~100 ms on a local file. Consequence: landmark pixel coordinates are in the
source video's frame space, which is also what the pipeline homography expects.

## D-15 (2026-09-22) — courtcam schema notes

`Event.made` is `bool | null` (`null` = not judged by the heuristic labeler, distinct from `false`). A profile may declare `court.templates: {variant: file}` instead of `court.template` (basketball needs one template per variant). Field names are unchanged from §4.5. courtcam owns `game.json` during a run (D-9); `out/_work/` holds intermediates the API never serves.

## D-16 (2026-09-22) — `WS /sessions/{sid}` also accepts the 4-digit pairing code

The phone companion (`/companion`, H4) only ever sees the code the TV shows, so it would
need a `GET /sessions/by-code/{code}` round trip before it could open the socket. Instead
the WebSocket route resolves `{sid}` as either a session id (`s_…`) or a pairing code
(four digits) — the two can never collide. No new route, no lookup, and an unknown value
still closes the socket with 4404, which the phone renders as "that code is not paired".
Consequence: `POST /sessions` stays the only session route; `AC-13` covers both forms.

## D-17 (2026-09-22) — live stage progress is merged into the read path, plus `progress`

D-9 said per-stage progress lives in the job record; this is how it reaches clients.
`GET /games/{id}` and `GET /games` merge the newest queued/running `process` job from
`data/jobs.json`: `status` becomes `processing`, the job's current stage is `running`
(`done` once its fraction hits 1.0), earlier stages are `done`, later ones `pending`, and
an additive `progress: {stage: fraction}` object rides along (absent when no job is
running). `game.json` is never written mid-run. `POST /games/{id}/process` is idempotent:
while a job for that game is queued or running it returns 202 with that job's id instead
of queuing a second run. `REPLAY_FAKE_PIPELINE_DELAY_S` (default 0) sleeps between the
two progress reports of each fake stage so the transition is observable in tests.

## D-18 (2026-09-22) — Lens distortion is out of Phase 1 scope

Every clip in the test corpus is ultra-wide or panoramic-stitched, so a single homography cannot sit on the court lines (see samples/real/RESULTS.md). The target footage is a phone 1x lens on a tripod, which is far less distorted. Phase 1 keeps the plain homography (least-squares over all clicked landmarks, optional extras allowed) and accepts loose on-court filtering on the corpus. Upgrade path: estimate k1/k2 from straight court lines with `cv2.calibrateCamera` before the homography. The uploader should tell users to film with the 1x lens, not 0.5x.

## D-19 (2026-09-22) — calibration takes any 4 landmarks the template knows, and the gate scales with the clicked span

Driving the real uploader on `basketball_kennesawwide_smoke.mp4` (2560×960 panoramic,
`corner_fr` off the bottom of the frame) failed three ways, all of them contract, not code:
`POST /games/{id}/calibration` demanded 4 `corner_*` **and** every name in
`court.landmarks`; the phone column showed the frame at 560 CSS px, so one tap was worth
~4.6 source px; and `MAX_REPROJ_PX = 5.0` is an absolute pixel bar. The fit on this
footage is barrel distorted (D-18) and ill-conditioned — ±0.5 px of click noise already
costs ~3.5 px of reprojection error, and guessing `corner_fr` on-frame costs ~20 px
(2000 px once the optional landmarks are in), far worse than leaving it out.
So: the API requires **4 landmarks the template knows** (`landmarks` ∪
`landmarks_optional`) and nothing more; the uploader walks the required list, lets any
single point be skipped ("Not visible") and reveals `landmarks_optional` behind a "More
points" button; the calibrate screen escapes the 560 px column; and the gate is
`max(5 px, 1 % of the clicked landmarks' pixel span)` — 25 px on this clip, still 5 px on
a 720p one. Measured: the polygon from hand clicks at 1920 px sits within ~25 px of the
one from exact landmarks, which is well inside `margin_m`. The web client no longer
carries its own copy of the threshold; a 200 from the API means "usable".
Consequence: `POST /games/{id}/calibration` no longer 400s on a missing `rim`.

## D-20 (2026-09-22) — the follow-cam window is a fraction of the COURT, and it is 16:9

`followcam.zoom` divided the _frame_ width, so the same 2.0 meant a tight crop on a 720p
clip and half of a 2560 px whole-court panorama. It now divides the court's pixel width
(`calib.court_polygon_px`, clipped to the frame; `croppath.court_px_width`), with
`croppath.MIN_CROP_W` as the floor and the frame width as both the cap and the fallback
when there is no calibration. The window is 16:9 in source pixels rather than the
frame's aspect, because the TV viewport is 16:9 — so `PlayerSurface` scales x and y
independently (identical to the old uniform scale on a 16:9 source) and
`render.render_crop` sizes its output from the crop rect instead of the source. Without
that pair a 2560×960 source came out stretched 1.5× vertically in follow mode.

## D-21 (2026-09-22) — `players.max` is a concurrency cap, not a roster size

The global top-N cap left 2–3 selectable players late in a clip because the best-scoring merged players were not contemporaneous. `identity` now accepts players greedily by score as long as no instant exceeds `players.max` concurrent players; the roster in `game.json` may exceed `max` (57 on the 240 s Kennesaw clip). Player ids are assigned in acceptance order. See samples/real/RESULTS.md "Concurrency cap".

## D-22 (2026-09-22) — No lens-distortion model; the badminton corpus clip fails on resolution, not barrel

Measured on the two net-sport clips: the 1x pickleball clip fits a 10-landmark homography at 2.8 px reprojection with ≤ 2.2 px paint drift, so nothing to correct. The 0.5x badminton clip compresses the 13.41 m court into 168 px of image height (≈ 3.4 px/m at the far baseline) with three overlapping line systems and two courts; undistortion cannot create the missing pixels. Decision: no `distortion.py`; `landmarks_optional` plus the reprojection gate handle usable wide-lens clips. Revisit only if a clip fails the gate with residuals that grow with radius from the image centre. Corollary for users and the corpus: a net-sport camera must be above and behind a baseline (≈ 3 m up), framing one court. Badminton stays "Tier 1 by code path" until a usable clip exists.

## D-23 (2026-09-22) — Auto-calibration proposes landmarks; the user still commits them

`courtcam.autocalib` proposes landmark pixels (backends: `vlm` via Anthropic SDK, `claude-cli` for keyless local dev, `lines` OpenCV snapping; `auto` chains them with a two-pass mirror-agreement gate and the D-19 reprojection gate). The API exposes it as a job (`POST/GET /games/{id}/calibration/auto`) and the phone page shows the proposal for accept or drag-adjust; `POST /calibration` remains the only commit. Status: on the panoramic corpus the model traces the wrong line (0 of 3 basketball clips within 20 px), so the UI currently hands users dots to drag rather than dots to accept. Next attempt: fit the court template to detected lines (classic) with the model as a prior; evaluate on phone footage when it exists.

## D-24 (2026-09-22) — Auto-calibration default is a template fit, not a vision model

`autocalib`'s `auto` backend is `templatefit`: line mask → Hough → merged lines → convex quads from line pairs matched to template rectangles whose edges are painted → scored by projecting the whole template against a distance transform → corner refinement. Measured: 10/10 landmarks within 12 px on the 1x pickleball clip and 1.8 px on the synthetic fixture, in 4–12 s with no key or network; the vision-model backends scored 0 of 4 at ~$0.26 and 3–14 min per clip and remain opt-in (`vlm`, `claude-cli`) or usable as a `--prior`. It fails on the three panoramic basketball clips because a barrel-distorted edge is a curve, and the hand-made homographies there score 0.23–0.27 against the paint themselves. `ok` is gated on the line score (≥ 0.90), not on reprojection error, which is 0 by construction for this backend. Next: run the fit on an undistorted frame once the distortion model (D-25 pending) exists.

## D-25 (2026-09-22) — One-parameter lens model, gated (supersedes D-22's "no distortion model")

The badminton auditorium clip (GoPro superview, camera beside the court in the net plane) met D-22's revisit criterion: pinhole residuals grow with radius (3 px at the centre, 25 px at 400–600 px). `courtcam.distortion` fits a division-model `k1` about the image centre at the calibrate stage from the clicked landmarks alone, gated at ≥ 8 landmarks and ≥ 30 % rms reduction, else `k1 = 0` (bit-identical to the previous payload; synthetic golden unchanged). `calib.json` gains additive `k1`, `image_size`, `lens_rms_px`; the court polygon becomes a 0.25 m polyline that curves with the paint; foot points are undistorted before projection. Result on that clip: rms 14.6 → 2.5 px, metre error 0.47 → 0.09 m max, roster unchanged (empty hall), team-by-side 0 errors in 14 026 samples. Ceiling: one parameter about the frame centre; `basketball_ceilingcam` (landmarks within 0.54 of the half-diagonal, 8 px/m depth, near corners occluded) leaves the gate closed and is not calibratable. Known follow-ups: `calibrate.homography()` RANSAC can report a 5-point consensus error on a barrelled frame; the API's calibration preview must call the lens-aware fit.

## D-26 (2026-09-30) — Badminton is one court (doubles-marked); `singles` is an alias

Virtually every hall is marked for doubles and the singles sidelines are already optional landmarks on the doubles template, so a second variant only bought the uploader a picker. `players {min 2, max 4}` is a concurrency cap (D-21), so singles games need nothing extra. `badminton.yaml` keeps one variant and adds `court.variant_aliases: {singles: doubles}`; `Profile.template()` and the API's variant check accept the alias, so existing game.json and landmarks files saying `singles` still load. `badminton_singles.json` is deleted.

## D-27 (2026-09-30) — Rally segmentation is motion-only: median player court speed with hysteresis

Net-sport rallies come from the identified players' court tracks: median speed over players on court (jumps > 6 m/s dropped, 2.5 s smoothing); a rally is a run above 0.5 m/s peaking ≥ 0.9 m/s, ending 0.5 s after the last peak and starting 1 s early for the serve; gaps < 1.5 s bridged, results < 2 s dropped. Thresholds are the profile's `rally:` block (`RallyCfg`). Audio onsets (plan §4.4) deferred: neighbouring courts make audio useless at the pickleball venue; `contacts` stays null. Measured at IoU ≥ 0.5 against hand labels: badminton 240 s P 1.00 / R 0.93 (0.92 / 0.86 on later tracks), badminton smoke 3/3, pickleball smoke 2/2 — in-sample (samples/real/RESULTS.md).

## D-28 (2026-09-30) — The stage list comes from the pipeline

`POST /process` sets `game.stages` to the running pipeline's own ordered list (`pipeline_adapter.stage_names`: courtcam's nine from `courtcam.pipeline.STAGES`, fake mode's five); clients render the keys they get and hardcode none. `progress` stays additive while a job runs (D-17). Before this the status page showed its own five stages "pending" for a whole real run. The game is saved before the job is queued, so a fast job can no longer be overwritten back to `queued`.

## D-29 (2026-09-30) — Calibration Adjust is correctable in place

The walk cursor is "first landmark at or after `step` that is neither placed nor skipped", so applying a proposal no longer parks it past the end. In Adjust, point chips select any point; "Not visible" and frame taps then act on the selection. On a handle a drag (> 5 px) moves the point and a tap goes to the point waiting to be placed (landmarks can sit 15 px apart inside one 44 px handle). Off-frame handles are clamped inside the frame. At ≥ 1100 px wide the controls take a side column so the frame fits a 1080 p viewport.

## D-30 (2026-09-30) — Play requests are held until playback starts

`PlayerSurface` keeps a play request (`wantPlay`) until the element fires `playing`, re-issues it on `canplay` or a 100 ms timer (max 5 retries; `NotAllowedError` not retried) and cancels it on pause; a pending request counts as playing for toggle. Chromium can leave a play promise interrupted by a load unsettled, so the fix cannot rely on the rejection.

## D-31 (2026-09-30) — Detection uses the GPU when present (yolo11m); BoT-SORT replaces ByteTrack

When `torch.cuda.is_available()` (ROCm included) and the backend is `pt`, detection runs on device 0 and swaps in `detection.gpu_model` (default `yolo11m.pt`); CPU machines are unchanged (yolo11n). `--model` overrides both. On an RX 9070 XT, yolo11m at stride 2 runs 4.1–4.6× realtime with 12–20 % more on-court detections and 11–26 % fewer raw tracklets than yolo11n; yolo11l adds nothing; stride 1 is slower and fragments more (the tracker buffer counts sampled frames). Tracker is `courtcam/botsort.yaml` (BoT-SORT, `track_buffer` 90, no GMC, no ReID): Kennesaw > 5 m id jumps 29 → 18, and it removes a badminton id swap ByteTrack made inside one tracklet. Supersedes D-5's ByteTrack/CPU clause. See RESULTS.md "Detection on the GPU".

## D-32 (2026-09-30) — Identity stitches using the roster and drops bystanders

Merging is closest-first and tolerates a 1 s handover overlap, in both the merge and the concurrency cap. After the cap, `identity._stitch` continues a team's ended lane with a newly appearing player only while that team is below its share of `players.max` (D-21), within 5 s and running reach (`merge_max_dist_m + 8 m/s × gap`), and only if the frame stays within `players.max` boxes; the gap is interpolated. Players who stay put (≥ 20 s inside a 0.5 m radius) or spend < 40 % of their life inside the painted lines are bystanders and never selectable: scorer's table, bench, the neighbouring pickleball court. Badminton auditorium 9 → 4 ids; Kennesaw bystanders 2.3 → 0 of ~9.4 selectable. Ceiling: referees still count as players; a stitched gap slides the box for up to 5 s.

## D-33 (2026-09-30) — Template auto-calibration: lens search with a physical-camera constraint

When the straight D-24 fit is not ok, the fit is re-run at k1 ∈ {-0.2, -0.4, -0.6}. Lines and quads are built undistorted; the mask is always read in source pixels, never rescaled (the old prestep shrank the court to a third at k1 = -0.65). Every candidate is snapped to the nearest pinhole camera (`templatefit.physical`), corners plus k1 are refined on explained paint, and lens winners and the straight fit are ranked by `covered` paint (each pixel once, so lines folded onto one bright curve are not rewarded). `ok` also requires camera skew ≤ 0.05: hand-clicked clips sit at 0.002–0.023, wrong fits at 0.1–1.1, and `basketball_parkwide` had been ok=True on a sheared wrong court. The line mask is cut to the picture only when letterbox bars exist. Off-frame required landmarks go to `Proposal.not_visible`, never invented. Result: badminton auditorium median 800 → 24.8 px (still ok=false), pickleball unchanged (2.4 px, ok), runtime 10–11 s when the lens search runs. Ceiling: D-25's centred one-parameter model — the hand-clicked auditorium court scores only 0.60–0.63 under it, a free distortion centre reaches 0.81; a principal-point offset in `distortion.py` is the next step toward < 10 px.

## D-34 (2026-10-06) — Local worker: per-game stage DAG over a content-hash cache

`services/worker` runs named, versioned stages, each declaring inputs, outputs, params, upstream stages and a resource class (`gpu | cpu | io`). Cache key = sha256(stage, version, item, params, content hash of every input); entries go to `$REPLAY_CACHE_DIR` (box default `/workspace/wt/replay-env/cache`) via temp-name + rename, so an entry is whole or absent; resuming is re-running the same command. Fan-out stages become one task per item. GPU tasks run one at a time holding the box-wide GPU lock only while computing; CPU tasks use a pool of 2. courtcam's nine stages are wrapped unchanged (byte-identical output, tested); their version is a hash of courtcam's sources. Media ≥ 16 MiB is hard-linked into the cache. Each task appends to `_work/worker.jsonl`; `perf` renders docs/perf.md. The API uses it with `REPLAY_PIPELINE=worker` (Step Functions + SageMaker Processing later, docs/aws-integrations.md).

## D-35 (2026-10-06) — Provider layout: Protocol + local implementation per module, AWS stubs in `aws.py`

Least disruptive: existing imports keep working. `REPLAY_PROVIDER_<NAME>=local|aws` selects through `providers.create`. Every AWS class mirrors its Protocol method for method (tested), raises NotImplementedError, and names its target service (S3, DynamoDB, Step Functions/SageMaker Processing, Bedrock Converse/Nova, Bedrock embeddings, Polly, Rekognition; speaker → a SageMaker endpoint hosting the local model). Local tts/llm/embeddings/face/speaker raise NotConfiguredError until their models land.

## D-36 (2026-10-06) — courtcam is published by subtree split

The Open Source mini-challenge repo is `git subtree split --prefix courtcam` via `scripts/split-courtcam.sh <remote> [branch]`, which refuses a dirty `courtcam/` or a missing LICENSE and prints a licensing checklist (MIT, no weights/footage, no workspace-only imports). ## D-37 (2026-10-06) — Fire TV client: react-native-tvos + shared tv-core, web build for tests

`apps/tv` is react-native-tvos 0.87 (New Architecture, Hermes) with react-native-video 6.19; the same source builds for the browser through react-native-web 0.21 + Vite so Playwright covers it without a device. Pure logic (API client/types/mock, spatial focus with overlap cycling, media clock, follow crop math, followSource, tracks cache, display helpers) lives in `packages/tv-core` (`type: module`, imported by relative path from apps/web and apps/tv; Metro reaches it via `watchFolders` + `nodeModulesPaths`). Platform code only in `apps/tv/src/platform/*.{web,native}.tsx` (config, keys, Media); PlayerSurface sits on Media; overlays sync to the shared clock. Follow mode is an Animated transform over the video. Fire TV remotes have no letter keys, so a MENU action row replaces web shortcuts and tagging uses an on-screen keyboard. Design in 1920-px units, ≥ 24 px text. Debug + release APKs (arm64/armv7, release signed with the debug keystore) build on hfbox; untested on a device (no KVM, no Fire TV attached). apps/web stays as the phone companion + browser TV harness.

## D-38 (2026-10-06) — Synthetic generator v2 and own MOT metrics

`courtcam.synth` renders articulated mannequins through a physical camera (K, R, t, k1) for basketball half/full, pickleball, badminton and volleyball (new Tier-1 profile, `margin_m` 2.0 and follow zoom 1.6 unvalidated), with a ballistic ball (makes pass the rim at 3.05 m), scripted possessions/rallies, gesture/voice/tap triggers and audio. It exports labelled-synthetic GT: boxes, COCO-17 keypoints, court positions, events, plays, triggers and the true calibration.json. Voice lines are pre-rendered with Kokoro-82M (Apache-2.0) and committed, so CI needs no TTS. Metrics are our own CLEAR-MOT/IDF1 on `lap` (py-motmetrics would add pandas + scipy and is unmaintained). Mannequins have feet, so the box-bottom foot point carries a real-detector-like 0.16–0.3 m median bias; court-error tests use median ≤ 0.25 m, per-sample ≤ 0.45 m. v1 fixture `samples/synthetic/basketball_half/` frozen; v2 goldens in `samples/synthetic/<sport>/<variant>/` are drift-tested.

## D-39 (2026-10-06) — Model stack on ROCm

SAM 2.1 via `transformers.Sam2VideoModel` in bf16 (fp32 is 10× slower); ASR = transformers Whisper (small default; faster-whisper is CPU-only here); TTS = Kokoro-82M (Apache-2.0; piper's maintained fork is GPL-3.0); LLM = llama.cpp HIP with Qwen3-4B-Instruct-2507 Q4_K_M and json_schema output, always followed by a deterministic validator (schema-valid output can still be semantically wrong); embeddings = open_clip / SigLIP; speaker = ECAPA. Every non-ultralytics torch model sets `torch.backends.cudnn.enabled=False` (MIOpen bugs on gfx1201, FL-9) and every GPU job runs as `flock … timeout N`. Paths, call snippets and timings in docs/models.md.

## D-40 (2026-10-06) — Tier C without a body model

Avatars are stylized capsule mannequins driven by 3D joints; no SMPL/SMPL-X/WHAM/GVHMR/HMR2 (registration or non-commercial licenses). Joints come from MotionBERT (Apache-2.0 code + weights, but Human3.6M-trained, so it lives only in the replay-side `render/` optional extra, never courtcam), with analytic placement (rays to the court plane + fixed bone lengths) as the license-clean fallback. ## D-50 (2026-10-06) — Play grammars are data; trigger resolution

## D-51 (2026-10-06) — Event detectors: pose shots, team-geometry possession, numpy audio

Shot = both arms up ≤ 0.9 s within 9 m of the rim, confirmed by a hoop-ROI burst ≥ 4 robust σ 0.3–2.2 s later; 2 vs 3 points from the release spot against the template's 3-pt zones; make/miss from what follows (other team's inbound = make; defensive rebound or same team shooting again = miss). Possession: offense is the team farther from the attacked rim. Audio is plain numpy (spectral-flux onsets, RMS dB, autocorrelation periodicity; not librosa); hype is loud AND aperiodic. ASR = whisper-small only over loud voiced segments; fuzzy matching with difflib. Defaults set from real measurements: `rally.audio_fusion: false` (real shuttle hits gave P/R 0.36 fused vs 1.00/0.86 motion-only) and `shot.extra_rims: false` (the far rim's ROI landed ~500 px off on Kennesaw). Ceilings: YOLO-pose misses the X gesture on ~68 px synthetic players (0/14), possession causes unreliable on real footage, net-sport auto score needs `winner_side`.

## D-52 (2026-10-06) — Grounded commentary; models behind a subprocess boundary

Commentary, advice and query answers come from deterministic templates over plays/events/score; that path is the guarantee. An LLM paraphrase (llama.cpp llama-server, Qwen3-4B-Instruct Q4_K_M, temperature 0, seed 0, json_schema output) ships only if `narrate.grounding.check` passes: every name, number, team, score claim and action verb must be present in the play's facts, else the line falls back to the template. The free-text query LLM only fills a json_schema filter (type, made/missed, value, rostered player, half, longest), never a time; a validator keeps only the fields the text grounds. Local model providers (tts Kokoro, embeddings SigLIP, speaker ECAPA, asr) run as `<venv>/bin/python -I providers/_runner.py <kind>` under `flock gpu.lock timeout 900` with `HF_HUB_OFFLINE=1`, so heavy deps stay out of the API venv and a model crash cannot take the API down. Search ranking: structured-filter hit, then word overlap with the play text, then RRF over SigLIP image/text cosines (SigLIP alone does not separate synthetic plays). Ceilings: the runner reloads the model per call (~6 s); llama-server holds the GPU lock while up, so TTS then runs with `REPLAY_MODEL_DEVICE=cpu`.

## D-53 (2026-10-06) — Full camera calibration

Focal from the floor homography (Zhang's constraints, square pixels, principal point at the centre), pose from K⁻¹H, both refined with `solvePnP` over floor + height landmarks (`rim_top` at 3.05 m, net-post tops at the sport's net height) inside a golden-section search on log f; k1 stays the D-25 lens-fit value. If the clicked l/r labels mirror the template the camera lands below the floor: the fit is redone in the x-mirrored world and the mirror folded into R (det R = −1, `mirrored: true`), and Tier B flips its output. The synthetic `rim` landmark is the floor point under the hoop; the hoop itself is `rim_top`. Ceiling: on wide/panoramic real basketball rigs the held-out hoop is still 50–90 px off (pinhole, centred principal point, one radial term is not enough); floors and feet are right, heights and ball arcs approximate. Upgrade: free principal point / k2 or more height clicks.

## D-54 (2026-10-06) — Tier B is 2.5D planar homographies, no GL

## D-59 (2026-10-06) — Tier C reconstruction pipeline

2D keypoints (synthetic GT, YOLO11m-pose on track boxes, or the `poses/` stage) are lifted to 3D by MotionBERT (FT_MB_release, h36m; perspective-corrected per-frame virtual camera, 243-frame windows at 50 fps, flip TTA), run as a subprocess in `venvs/lift` and used only when present (`tierc_method=auto`); courtcam and the worker never import it. Clean-up: Savitzky-Golay (separate pose/root windows), median bone lengths, foot-contact pinning with two-bone IK and smootherstep blends, torso-capsule separation push held at peak then Gaussian-smoothed. Output `scene/{play_id}.json` (`replay.scene.v1`); basketball ball arc wrist → rim (made: through the net; missed: off the front rim; unknown: stops at the rim, which is the default because `made` is null until a user confirms). Renderer: OpenCV painter's algorithm, jersey-coloured capsule mannequins, labelled "3D reconstruction - stylized (MotionBERT lift)"; headless moderngl measured 3.6 ms/frame vs 6–47 ms but not adopted (extra dependency + GL context; painter meets the budget). ## D-68 (2026-10-06) — X gesture: trust confident crossings, make uncrossed holds outlast a release

## D-70 (2026-10-06) — Identity: cut cross-team jersey swaps, link tracklets by global assignment

## D-75 (2026-10-06) — Navigable 2.5D replays: a scene package rendered live on the client

The user asked to navigate real-footage replays from different angles and to optimise for the eventual native Fire TV app. Pre-rendering an angle grid was rejected: every angle cut reloads a video source, which perf.md already flags as the slow path on Fire TV, and movement would be discrete jumps. A `scene` worker stage (one task per play, cached, opt-in, after `segment` + `plate`) writes `replays/{play}/scene/` as `replay.scene_package.v1` (docs/scene-format.md; `replay.scene.v1` is Tier C's, D-59):

- the Tier B floor and backdrop as RGBA PNGs with world quads; alpha marks what the real camera saw;
- one H.264 yuv420p atlas video per highlight holding every visible player's SAM cutout, rectified onto its billboard plane and packed into a fixed cell grid, colour left and mask-as-luma right, ≤ 2048×1024, 1 s GOP. On Fire TV this is one hardware decoder feeding a GL external texture; on the web, a VideoTexture;
- layout.json: the frame→cell map, foot points, billboard rects, hoop/net/modelled ball, the real camera, and an orbit envelope with presets.

Billboards face the real camera: exact at the real view, and within 0.03 silhouette IoU of viewer-facing inside ±30° on synthetic ground truth.

The envelope is derived per package so the viewer never sees the unseen side:

- visible players turn ≤ 30° in azimuth and ≤ 20° in elevation;
- plate coverage stays ≥ 0.85 of the real view;
- magnification stays ≤ 2×.
  On the real corner and courtside rigs this is small: about ±6–12° of azimuth and +4–15° of elevation.

A CPU reference renderer (`replay_render.virtual.scene`) is ground truth for both clients. From the real camera it reproduces players at 28 dB / SSIM 0.90 on Kennesaw.

Served by `GET /games/{id}/scenes[/{play}]`, files through /media with Range; the replay manifest carries `scene_url`.

Ceilings:

- one backdrop wall, so side halls are void;
- static objects are baked flat into the floor;
- hoop heights are off on panoramic rigs (D-53);
- no tracked ball;
- the envelope is a sampled box, not proven inside.

## D-77 (2026-10-06) — Free view: one shared camera module, a raw WebGL2 renderer on web and a GL Fabric view on Fire TV

## D-82 (2026-10-22) — Follow player: the TV runs the camera from the tracks, and you pick on the video

Problem, measured on the CC BY game on a Fire TV Stick: the camera panned once and then parked, the ring showed up late or never, and the camera took about 2 s to zoom in after Select. Causes:

- The game has 59 track ids for about 10 players on court, and the median id lives 36 s. The old chip carousel listed all 59, so picking an id that was not on court at that moment gave no box and no ring.
- The server crop path (`crops` stage) holds its last box after the id ends, so the camera parks on empty floor. It was also fetched only after Select, which is where the ~2 s went.
- The ring was drawn by React at the 30 Hz track rate while the camera moved every frame, so the two drifted apart.
- The clock jumped forward by the length of a pause after Play (it extrapolated from the report taken before the pause). That jump made the camera seek and put the ring in the wrong place.

Decisions:

- **The camera runs on the TV** (tv-core `createFollowCam`), stepped every animation frame from the track chunks the TV already has. It follows with a critically damped spring: 0.5 s lead from the player's velocity, a small dead zone, and zoom set by the smoothed box height. It starts wide and eases in. Seeks snap, and zoom-out eases back to exactly the full frame. The crop-path API stays, but the TV no longer uses it.
- **One loop moves the camera and the ring** (PlayerSurface), through Animated values, without re-rendering the screen. Only values that changed are sent. Short dropouts (under 0.3 s) keep the ring on; longer ones fade it out. A hand-off eases over 0.2 s, so the ring does not flicker or snap.
- **Hand-off to a new id only when it is unambiguous.** The new box must be within reach, clearly nearer than any other (by half a box height), on the same team when teams are known, and new since the gap or born on top of the player. The tracker's id breaks happen in crowds, where "the nearest new id" was the wrong person (checked by eye on real frames). So on the basketball game nothing qualifies, and the camera says so. Past 1.5 s with no box it widens and the chip says "Lost sight of X · Select Pick again". Select opens the picker at the player nearest where they were last seen. Truly long continuity needs server-side re-identification (tracklet merging), which is not built yet.
- **Picking happens on the video, not in chips.** Follow player (or Pick another player) pauses and shows a marker on every tracked player. The arrows move between them spatially, Select follows (and playback resumes if it was playing), and Back cancels. Labels show the enrolled name, otherwise "Player N", only on the focused or named marker. Markers and the ring use the team colours (`teamColorMap`). Do more's chip view stays for Player POV.
- **Clock:** the wall reference resets while paused, and extrapolation is capped at 0.5 s.

Measured on real games:

- **Fire TV, CC BY basketball:** the first frame captured after Select already shows the ring and "Following". The camera has zoomed in by the next capture, about 1 s later (`adb input` itself takes about 0.9 s, so this is an upper bound). In the browser test, the ring and camera respond within 200 ms of the key. Jank (gfxinfo, 10 s windows): wide playback with the ring 0.5–0.8% (4.0% before skipping unchanged values), following a moving player 8–15%, p90 15–19 ms. The old app's 2.0% was measured with the camera parked and no ring, so it is not a like-for-like baseline.
- **Offline, 60 random picks × 30 s at 60 fps:** the box stayed inside the camera window 100% of the time on both games. The ring was on 67.6% of the time on basketball (the old app also had 67.6%, but with its camera parked on nothing) and 74.1% on the local-only volleyball clip (73.0% before), with one hand-off (checked: the same person). Volleyball frames stay local (D-76).

## D-86 (2026-10-22) — Cloud API: a route pulls only the files it reads, never the whole game

- **Why.** On S3 (D-80) a Lambda instance mirrors game files on demand. `storage.game_dir(id)` mirrors the whole game: one LIST, then one GET per object, including every moment thumbnail and storyboard sheet.   - `/hype`: 10.7 s, only to answer 503, because Lambda has no `replay_render`.
  - `/commentary`: 8.4 s.
  - Warm, every Watch-open request takes 0.3–0.6 s.
- **Rule.** `LocalStorage.game_dir_with(id, *rels)` mirrors only the named files or folders (local disk: a no-op), and every route names what it reads:
  - review queue: events and tracks
  - hype: `load_game`'s files plus audio, poses and the video
  - rallies and condensed: events, plays, condensed.json and the rendition
  - vertical exports: their folder, plus `load_game`'s files and clips to create one
  - score: edits.json
  - commentary: game, events, plays, score, and `commentary/` once
  - search: embeddings
  - profile careers: each linked game's docs, tracks, hype, clips and media
  - face match: game, tracks and the video
- **Writes.** The write routes pull edits.json and only the files they rewrite: player name or link (edits.json; a merge also tracks, crops, events), event answers (plus events, score), bookmarks, taps, trims and score.
- **Ordering.** `/hype` and `POST /exports/vertical` check for `replay_render` before pulling anything, so the cloud 503 is immediate.
- **Folder coverage.** `S3Storage._pull` treats a folder already mirrored in this request as covering the files under it: one LIST for all of commentary's audio files, not one per play.

## D-87 (2026-10-22) — TV and phone clients: retry throttles, at most 4 requests in flight, Watch extras after the first frame

- **Why.** The account's Lambda concurrency is 10, shared by every TV and phone. A Watch open sent 7 requests at once (peak 7 in flight locally, about 10 with the tracks chunks on Lambda latency), and five opens at once got 429s. We make no AWS change (no quota request, no reserved concurrency); the clients ask less and wait their turn.
- **Retry (`packages/tv-core/src/retry.ts`, used by the TV client and the phone's `apps/web/src/api/phone.ts`).**
  - A throttle is a 429, or a 503 with Retry-After or a body matching "rate exceeded / too many requests / throttl". Our API's own 503 ("replay_render is not available") is an answer and is not retried.
  - Up to 4 tries. The wait is Retry-After (seconds or an HTTP date) plus up to 100 ms of jitter, else 100 ms + random·300·2^attempt. The client stops when the next wait would pass 4 s from the start, and returns the last response, so the screen's existing error shows (the spinner stays up until then).
  - Only safe-to-repeat requests: GET/HEAD/OPTIONS/PUT/PATCH/DELETE, plus the POSTs the API treats as reads or makes idempotent: search, query, condensed render and vertical export. Other POSTs (upload, clip, tap, bookmark) are sent once.
  - Not retried: network errors (fetch TypeError). A browser cannot read Retry-After cross-origin unless the response exposes it (`Access-Control-Expose-Headers`); without it the jittered backoff is used. Lambda's own 429 is answered before FastAPI, so exposing it there would mean changing the Function URL's CORS config, which is an AWS change and was not made.
- **At most 4 in flight** per app (a module-level FIFO). A slot covers one request, not its backoff. Ceiling: a hung request holds its slot until Lambda's 30 s timeout or the browser gives up. Media (mp4, images) does not go through it; the tracks chunks (`/media` JSON, Lambda 302s) do.
- **Watch open.** Game, renditions and moments load at once. Replays, commentary, hype and rallies wait until the player has a duration (first frame), or 3 s after the game loads, whichever comes first.
- **"Not available" is remembered.** A 503 from `/hype` or `/rallies` whose message says "not available" is kept per game for the client's lifetime and not asked again. A condensed render clears the rallies entry.
- **Polling.** Clips' export poll went from 1 s to 3 s. Others are already gated: Watch polls the game every 10 s and Home every 15 s, only while it is processing. Watch's 1 Hz `now` goes to an open pairing WebSocket, not HTTP.
- **Measured** (web build, `apps/tv/e2e-evidence/WATCHOPEN-requests.spec.ts`, local API without `replay_render` so hype and rallies 503 as on Lambda): before, 11 requests and peak 7 in flight, all 7 API reads leaving at ~310 ms. After, 11 requests and peak 4: game, renditions and moments at 367 ms, storyboard and 2 tracks chunks at 432 ms, then replays, commentary, hype and rallies at 539 ms after the first frame.
- **Tests.** TV-35: retry unit tests (Retry-After honoured, cap, our 503 vs a Lambda 503, a POST sent once), the in-flight cap (10 requests, peak 4, in order), hype and rallies asked once per game, two e2e runs through the real HTTP client with routed 429s (recovers to "Connected · 2 games"; past the cap shows "Not reachable" within ~7 s), and the mock Watch order. The mock API never goes through fetch, so the throttle e2e uses routed 429s instead of the mock's ApiError.
- Client-only: needs a new APK and web deploy, no Lambda change.

## D-90 (2026-10-22) — Shots, makes and score from the ball at the rim; highlights from detected plays; play logs for truth and notes

(Assigned as D-87; that number was taken in this file by the client-retry entry, so this is D-90.)

**Problem.** On the live CC BY game the score never moved and Highlights were mostly wrong. Shots came from a pose release plus a pixel burst at the rim; make/miss from what happened next (inbound vs rebound). Measured against a hand annotation, the Nottingham Q1 clip had 17 detected shots for 10 real ones, 1 of 4 makes labelled at all, and a final score of 0-0 for a true 3-4.

**Ground truth first.** `samples/truth/nottingham_q1.json` and `nottingham_q3.json` (`replay.playlog.v1`, `use: evaluation`, label "hand annotation (ground truth for evaluation)"). Each shot was read frame by frame from hoop zooms at 10-30 fps. The in-arena scoreboard and both shot-clock repeaters, read at 1 fps, are an independent check: every make in the files moves the board. They hold facts read from the CC BY video plus its attribution, not frames. They are never shown in the app. Q3 was annotated before any change was measured on it and is the hold-out.

**Harness.** `courtcam eval-events -o GAME --truth FILE [--json]` (`courtcam/eventeval.py`) reports:

- shots: precision and recall within 1.5 s of the rim time; a detection of a shot that does not count (after the whistle) is neutral;
- make/miss accuracy, and make precision and recall;
- points on made shots;
- team agreement under the better of the two team mappings;
- final-score error (absolute, summed over both teams);
- highlights: precision@5 (a top-5 candidate window holds a made field goal, block or steal) and made field goals inside the top 5.

**Changes, each measured on Q1.**

1. **Ball at the rim (`courtcam/ball.py`).** A COCO detector is no use here: YOLO11x `sports ball` found the ball in 3 of 91 full frames. Classical CV in a box around each rim the calibrated camera projects is enough. Per frame, it keeps ball-coloured, ball-sized blobs that moved against a running background, in rim units. Details:
   - The hue range wraps through red: a ball in shadow reads hue 170-176.
   - Phase-correlation registration absorbs camera shake, which had made the rim itself a "ball".
   - The projected rim is snapped onto the painted rim: the far rim projected 15 px high.
   - Each visit to the rim is a shot. A visit needs the ball to come down into the box, or to stay for 6 frames (rolling on the rim), so a pass across does not count.
   - Make = the ball crosses the plane 0.3 rim below the rim downward, within 0.55 rim of its middle, then is seen lower in a cone under that point within 0.7 s.

## D-94 (2026-10-22) — A court fit the people disagree with filters nobody (`court.trusted`)

Context: phone footage of a half court. The court fit decides who is "on court", so a wrong fit drops real players and keeps the crowd.

- **Autocalib is wrong on every half-court phone frame tried.** Template backend, `half` variant, on the cc3x3 clip, Nottingham (whole frame and left and right half crops), the JaiArtHub 2v2 clip (below) and the 2v2 park proxy: every proposal is `ok=False`, and the lines it reports are random lines in the scene. - **So the pipeline checks the fit against the people instead (`court.fit_check`).**

## D-96 (2026-10-22) — No basketball block detector yet: the signals we have cannot tell a block from a contested shot; the phone's "Watch it" plays on the TV when one shows the game

Context: round 4 on D-95. The coordinator asked for two things:

- A block detector to lift the highlights ceiling. It should combine a shot start, the ball turning back before the rim, and a defender's hands at the ball. It is to be checked on the two truth blocks (Q3 59.7 s, park dev 59.2 s), and it must add no false blocks elsewhere.
- A phone "Watch it" in Review.

**Block detector: measured, not shipped**

- **What the ball can and cannot show:** the ball is watched only in the box around each hoop: ±5 rim radii across, 7 above to 3 below (about ±1.1 m, 1.6 m above to 0.7 m below the rim). A block away from the rim never shows in the ball data.
  - Q3 59.7 s happens about 2.7 m out; the ball is never seen there.
  - The park dev block (59.2 s) is at the rim. Its ball path rises from below the rim, then comes down beside it. That is the same shape as a layup (park dev 127.8 s make, 94.2 s miss; 3x3 13.7 s make).
  - Of the 33 arrivals on the four clips, 8 rise from below without a descent, and only one of them is the block.
- **Pose candidates:** an arms-up release within 3.5 m of a rim, with no ball arrival within 2.5 s after it and no shot in the 2 s before it, plus an opponent within 1.2 m with arms up. We measured them on the full pipeline for Q1, Q3, 3x3 and park dev. Park dev was newly run with tracking and pose on a ground plane from people's heights, as in D-89; the floor point under the rim came from the hand-placed hoop.

  | clip     | candidates                                      | true blocks found     |
  | -------- | ----------------------------------------------- | --------------------- |

  | 3x3      | 0                                               | –                     |

  - Q3 59.2 s: no opponent is tracked within 1.5 m of the driver; the 1080p wide view gives these players a torso of about 20 px.
  - Park dev 59.0 s: the release is followed by a ball "arrival" (the false make at 59.18 s, D-95), so it is not a candidate.
  - Loosening the rule (any team, 1.5 m, no arms-up) finds Q3 59.2 s, but with 8 more candidates on Q3 and 10 on Q1, none of them a block.

- **The defender's hand over the shooter's:** we measured the defender's top wrist above the shooter's top wrist, in torso lengths, within ±0.3 s of the release.
  - The park dev block reads +0.37 to +0.57.
  - The contested make at park dev 23.6 s reads +0.59.
  - The false candidates read +1.0 to +2.6 (Q1 65.2 s, 236.6 s; Q3 239.8 s).
  - Pose alone does not separate a block from a contested shot.
- **Decision:** we ship no block event. A detector at zero recall with false blocks would put wrong plays at the top of highlights (`NOTABLE_VALUE` block .7) and wrong Blk counts.
  - Everything downstream already handles `block` events: stats Blk, the highlight value, the "Block" moment label, and "Was this a block?" in Review.
  - A future detector that sees the ball across the court only has to emit them.
- **Upgrade path:** a ball detector over the whole frame (a learned one; colour alone confuses red kits and skin), so the ball's turn-back can be seen where blocks happen. Or a higher camera, with the same pose rule re-measured.
